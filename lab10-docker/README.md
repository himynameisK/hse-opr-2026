# Занятие 10 · Docker 1

Готовое веб-приложение надо упаковать так, как требует контракт проектной
работы: образ, compose, `/health`, порт наружу, CI, `.dockerignore`. После
этой лабы то же самое вы делаете со своим проектом без подсказок.
Обязательные — **1–5**, задача 6 — плюсом.

## Где это делается

На своей машине с запущенным Docker: Docker Desktop (macOS, Windows) или
docker engine с плагином compose (Linux). Права root не нужны. Ещё нужен
Python 3.8+ — только для `check.py`, приложение живёт в контейнере.

```bash
git pull && make lab10       # без make: bash lab10-docker/setup.sh
cd ../opr-lab10
docker info                  # должен ответить без ошибок
```

Развернётся рядом с репозиторием курса, в `../opr-lab10` — точный путь
скрипт печатает последней строкой, `Готово: …`.

```text
app.py              приложение — НЕ править
requirements.txt    зависимости с закреплёнными версиями — НЕ править
.env                «секрет» — в образ попасть не должен
venv/  __pycache__/ debug.log    мусор — в образ попасть не должен
check.py            проверка
README.md           этот файл
```

Пишете вы — рядом с `app.py`, как в корне своего репозитория:

```text
Dockerfile
.dockerignore
compose.yaml
.github/workflows/ci.yml
```

## Приложение

Счётчик посещений на Flask, данные в redis.

- `GET /` — увеличивает счётчик в redis и отвечает `Посещений: N`;
- `GET /health` — `200 ok`, если redis отвечает на PING, иначе `503`.

Настраивается только переменными окружения — так принято для контейнеров:

| Переменная | По умолчанию | Что это |
|---|---|---|
| `HOST` | `127.0.0.1` | на каком адресе слушать |
| `PORT` | `8000` | на каком порту |
| `REDIS_HOST` | `localhost` | где redis |
| `REDIS_PORT` | `6379` | его порт |

Запускается так: `pip install -r requirements.txt`, затем `python app.py`.
Значения по умолчанию подобраны для запуска на ноутбуке. В контейнере
как минимум два из них неверны — какие и почему, вы должны объяснить на приёме.

## Задачи

**1. Образ.** `Dockerfile` в корне; образ собирается командой `docker build .`
без ручных шагов. Контейнер из него, запущенный с `-p`, отвечает на `/health`
с хоста. Порт приложения в контейнере — 8000, укажите его в `EXPOSE`.
Проверка запускает контейнер *без* redis и ждёт с хоста ответа `503`: это и есть
«приложение живо и честно говорит, что базы нет».

**2. Без мусора.** `.dockerignore` такой, что в контекст сборки и в образ
не попадают `.env`, `venv/`, `__pycache__/`, `debug.log`. Удалять их из каталога
не надо — у вас в проекте они тоже будут лежать. Проверка смотрит и что уходит
демону при сборке, и что оказалось внутри образа. В проекте рядом нужен ещё
`.gitignore` с тем же мусором — здесь его не проверяют, в проектной работе проверят.

**3. compose.** `compose.yaml` с двумя сервисами — **`app`** (собирается из
вашего `Dockerfile`) и **`redis`** (официальный образ `redis:7-alpine`).
Порт `app` опубликован на хост. После `docker compose up -d` `/health` отвечает
`200`, а `/` — `Посещений: 1`, `2`, `3`. Имена сервисов именно такие: проверка
обращается к `app`.

**4. Данные переживают перезапуск.** У redis именованный том, подключённый
к `/data` — там redis хранит данные. После `docker compose down` (без `-v`)
и снова `up` счёт продолжается, а не начинается с 1. Redis сам сохраняет
снимок при штатной остановке; чтобы данные переживали и падение, включите
журнал: `command: redis-server --appendonly yes`.

**5. CI.** Файл `.github/workflows/ci.yml` (имя любое, `.yml` или `.yaml`):
запускается на каждый `push`, одна задача на `ubuntu-latest`, в ней шаги:
`actions/checkout`, затем сборка образа — `docker build …` или
`docker/build-push-action`. Пишите по слайду лекции. Проверка не запускает
Actions, а разбирает YAML: закомментированный шаг или `docker build` не на своём
месте не засчитаются. Зелёный прогон на GitHub — уже в проектной работе.

**6. Плюсом: порядок запуска.** У redis `healthcheck` через `redis-cli ping`,
у app — свой `healthcheck` на `/health` и `depends_on` на redis с
`condition: service_healthy`. `docker compose ps` показывает app `healthy`.
В `python:3.12-slim` нет `curl` — `/health` из healthcheck можно спросить
самим питоном (`python -c` и `urllib.request`). Интервал по умолчанию — 30 с,
поставьте поменьше.

## Как проверить

```bash
python3 check.py           # все задачи
python3 check.py 3         # только третья
python3 check.py 3 4       # третья и четвёртая
```

На Windows — `python check.py` или `py check.py`.

Проверка всё делает по-настоящему: собирает образ, запускает контейнер,
поднимает ваш compose. Первая сборка — пока pip качает пакеты — минуту-две,
дальше быстрее. Порт на хосте проверка берёт случайный свободный (ваш `8000:8000`
подменяется только на время проверки), имя compose-проекта — своё на каждый
прогон, и в конце всё за собой убирает: контейнеры, тома, сети, свои образы.
Ваш собственный `docker compose up` она не трогает.

```text
Задача 1: FAIL
  ждали: GET http://127.0.0.1:53817/health → 503 (redis в этом тесте нет)
  получили: RemoteDisconnected: Remote end closed connection without response
  подсказка: внутри контейнера приложение слушает 127.0.0.1 — …
```

Под `FAIL` — что ждали, что получили и подсказка. Руками то же самое:

```bash
docker build -t counter .
docker run --rm -p 8000:8000 counter            # в другом окне: curl -i localhost:8000/health
docker compose up -d --build && curl localhost:8000/
docker compose logs app
docker compose down                             # -v — удалить и том с данными
```

Если `check.py`, `app.py` или README случайно испортились:
`bash lab10-docker/reset.sh` из каталога курса вернёт их как было,
ваши файлы не тронутся.

## Приём

`PASS` по задачам 1–5 (6 — плюсом) и устный ответ «почему так»: что значит
`127.0.0.1` внутри контейнера, почему `COPY requirements.txt` идёт раньше
`COPY . .`, что уезжает демону без `.dockerignore`, почему `REDIS_HOST: redis`
работает, куда делись бы данные без тома.
