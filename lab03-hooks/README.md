# Занятие 3 · Хуки и проверки на стороне GitHub

Git умеет запускать ваш скрипт в момент коммита — у вас на машине. GitHub умеет
запускать ваш скрипт у себя, в ответ на событие в репозитории. Разница не в том,
что удобнее, а в том, что первое снимается одним флагом, а второе — нет.

Первое задание делается в учебном репозитории: там хук, он локальный.
Остальные три — **сразу в вашем репозитории на GitHub**, по-настоящему.
Actions живут на GitHub, и в учебном каталоге они не запустятся никогда,
поэтому делать их там значило бы писать в стол.

## Подготовка

Учебный репозиторий, из корня репозитория курса:

```bash
make lab3                   # если make нет: bash lab03-hooks/setup.sh
cd ../opr-lab03/shop        # путь скрипт печатает сам
```

Хуков в нём нет: вы напишете их сами.

**И свой репозиторий на GitHub.** Подойдёт любой: учебный, pet-проект,
конспекты. Склонируйте его рядом — работать будете в двух каталогах сразу.

Одно условие: репозиторий должен принадлежать **вам лично**, а не организации.
`gitleaks-action` спрашивает у GitHub тип владельца, и для организации требует
лицензионный ключ. Ключ бесплатный, но выдаётся по заявке через форму и приходит
письмом — на занятие вы его получить не успеете. Без ключа экшен не сканирует
ничего: падает сразу со строкой `missing gitleaks license`. Для личного аккаунта
ключ не нужен. Красный крест от лицензии выглядит ровно так же, как красный крест
от секрета, поэтому проверьте владельца до того, как начнёте искать ошибку
в своём yml.

## 1. Два хука в `.githooks` — в учебном репозитории

В каталоге `.githooks` уже лежат **каркасы обоих хуков**, на Python. Всё, что
достаётся из git, в них написано: вам остаются только условия. Мест с пометкой
`ЗАПОЛНИТЬ` три — два в `pre-commit`, одно в `commit-msg`.

Git запускает хук как обычную программу. Требования два: файл исполняемый
(`chmod +x` уже сделан) и с шебангом в первой строке. Язык не принципиален —
проверка смотрит на поведение, так что переписать на bash никто не мешает.

### `pre-commit` — не даёт закоммитить секрет

Из git уже вытащено:

```python
# files — пути файлов, которые уходят в коммит
files = git("diff", "--cached", "--name-only", "--diff-filter=ACM").split()

# added — добавленные строки индекса, уже без ведущего '+'
added = [line[1:] for line
         in git("diff", "--cached", "--diff-filter=ACM", "-U0").splitlines()
         if line.startswith("+") and not line.startswith("+++")]
```

Почему `--cached`, а не файлы на диске: хук должен смотреть на то, что **уходит
в коммит**. Вы могли подготовить чистую версию через `git add`, а потом дописать
в файл токен — в индексе его не будет, и наоборот.

**ЗАПОЛНИТЬ 1.** Пройтись по `files` и отклонить `.env` и любые `.env.*`.

**ЗАПОЛНИТЬ 2.** Найти в `added` присваивание секрета с непустым значением:

- поймать `API_KEY="AKIAIOSFODNN7EXAMPLE"`, а также `TOKEN=`, `SECRET=`
  и `PASSWORD=` с непустым значением;
- поймать их же **с приставкой**: `SLACK_TOKEN=`, `DB_PASSWORD=`,
  `AWS_SECRET_ACCESS_KEY=`. Имя секрета редко бывает голым;
- **не** поймать строку «Не коммитьте токены и пароли» в обычном тексте;
- **не** поймать `GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}` — это ссылка
  на секрет, а не секрет. Она встретится вам в задании 3, и хук, который
  её блокирует, придётся чинить.

Вся разница между ними — знак `=` и непустое значение после него. Ищите
присваивание, а не слово.

Отказ оформляется так: напечатать причину в `sys.stderr` и поставить
`status = 1`. Ненулевой код возврата отменяет коммит.

### `commit-msg` — требует номер задачи

Из git уже вытащено:

```python
message = open(sys.argv[1], encoding="utf-8").read()
first_line = message.splitlines()[0] if message.splitlines() else ""
```

Git передаёт этому хуку **один аргумент** — путь к файлу с сообщением. Не текст,
а путь: сообщение надо прочитать из файла, что каркас и делает.

**ЗАПОЛНИТЬ.** Принять `SHOP-12 Добавить расчёт скидки`, отклонить
`Добавить расчёт скидки` и `shop12 добавить скидку`.

### Включить

Оба скрипта закоммитьте. Хуки не переносятся клонированием сами по себе,
поэтому их кладут в репозиторий и включают одной командой:

```bash
git config core.hooksPath .githooks
```

Пока вы её не выполните, `.githooks` для Git — обычный каталог с файлами,
и коммиты будут проходить как ни в чём не бывало. Это первое, что надо
проверять, когда «хук не работает».

Вторая частая поломка — шебанг. Скрипт развёртывания подставил тот интерпретатор,
который нашёл у вас; если вы правите файл руками, проверьте, что команда из
первой строки действительно существует: `python3 --version`. Если хук молча
не срабатывает — смотрите `core.hooksPath`, если падает с `cannot exec` —
смотрите шебанг.

## 2. Уведомление в Telegram — в вашем репозитории

Дальше всё происходит в вашем репозитории на GitHub. Первым делом перенесите
туда хуки — они и были задуманы как инструмент, который остаётся с вами:

```bash
cp -r ../opr-lab03/shop/.githooks .        # из каталога вашего репозитория
git add .githooks && git commit -m "хуки"
git config core.hooksPath .githooks
```

Убедитесь, что хук жив на новом месте: попробуйте закоммитить строку с токеном.

Хук работает у вас на машине. Теперь сделаем то, что работает **на стороне GitHub**
и продолжает работать, когда ваш ноутбук закрыт: при отправке в репозиторий
в Telegram прилетает сообщение.

Сервер для этого не нужен. GitHub Actions — это виртуальная машина, которую
GitHub поднимает у себя на время прогона. Она сама звонит наружу, в Telegram,
а входящих соединений к вам нет.

**Заведите бота.** В Telegram напишите `@BotFather`, команда `/newbot`, имя
и username (он должен оканчиваться на `bot`). В ответ придёт токен.

**Узнайте chat_id.** Бот не пишет первым — сначала отправьте ему любое сообщение,
потом:

```bash
curl -s "https://api.telegram.org/bot<ТОКЕН>/getUpdates" | python3 -m json.tool
```

В ответе найдите `"chat": {"id": ...}`. Пустой `result` означает, что боту ещё
не писали.

**Положите оба значения в секреты репозитория** на GitHub:
Settings → Secrets and variables → Actions → New repository secret: `TELEGRAM_BOT_TOKEN` и `TELEGRAM_CHAT_ID`. В файлы их класть нельзя,
и проверка за этим следит.

**Готовый workflow — ниже.** Положите его в `.github/workflows/telegram.yml`.
Разбираться с отступами YAML не надо, это не цель задания.

```yaml
name: telegram
on:
  pull_request:
    types: [opened, reopened]
jobs:
  notify:
    runs-on: ubuntu-latest
    steps:
      - name: Сообщить в Telegram
        env:
          TOKEN:  ${{ secrets.TELEGRAM_BOT_TOKEN }}
          CHAT:   ${{ secrets.TELEGRAM_CHAT_ID }}
          REPO:   ${{ github.repository }}
          ACTOR:  ${{ github.actor }}
          BRANCH: ${{ github.ref_name }}
        run: |
          TEXT=$(printf 'Событие в %s → %s, автор %s' "$REPO" "$BRANCH" "$ACTOR")
          curl -sS -X POST "https://api.telegram.org/bot${TOKEN}/sendMessage" \
            --data-urlencode "chat_id=${CHAT}" \
            --data-urlencode "text=${TEXT}" \
            -o r.json -w 'HTTP %{http_code}\n'
          jq -r '"ok = \(.ok)"' r.json
```

**Ваша работа — поменять триггер.** Сейчас файл срабатывает на открытие pull
request. Сделайте так, чтобы сообщение приходило **на каждую отправку**
в репозиторий.

Меняется не один ключ, а две строки. Строка `types: [opened, reopened]`
относится к `pull_request` — это его «виды событий»: открыли, переоткрыли.
У `push` видов событий нет вообще, он либо случился, либо нет. Оставите
её — GitHub откажется читать файл, и workflow не запустится ни разу.

Должно остаться ровно две строки:

```yaml
on:
  push:
```

Это не формальность: `push` и `pull_request` — разные события. `git push`
сам по себе pull request не создаёт, поэтому с исходным файлом при отправке
ветки ничего не произойдёт. Пока не откроете PR руками.

Закоммитьте и запушьте. Файл новый, поэтому `git add` обязателен: `git commit -a`
неотслеживаемые файлы не видит и соберёт коммит без вашего workflow — а вы
будете искать ошибку в файле, которого на GitHub нет.

Сообщение придёт в Telegram. Его текст и вывод шага идут в `SUBMISSION.md`.

Ни одного чужого экшена в этом файле нет — только `curl` и `jq`, они на раннере
уже стоят. Сравните с заданием 3: там `uses:` тянет чужой код, который выполнится
в вашем репозитории.

## 3. Workflow, который ищет секреты — там же

`pre-commit` живёт на вашей машине и снимается флагом. Проверка на стороне
GitHub так не снимается: она смотрит на то, что уже пришло в репозиторий, и
ставит красный крест в Pull Request.

Создайте `.github/workflows/gitleaks.yml`. Он должен:

- запускаться на `push` и на `pull_request` (`workflow_dispatch` уже в каркасе);
- забирать историю целиком: `actions/checkout@v6` с `fetch-depth: 0`;
- звать `gitleaks/gitleaks-action@v3`;
- передавать экшену `GITHUB_TOKEN` через `env:`.

Структура та же, что у `telegram.yml` из задания 2 — держите его рядом как
образец. Каркас, чтобы не воевать с отступами:

```yaml
name: gitleaks

on:
  # ЗАПОЛНИТЬ: два события — на них проверяются присланные коммиты
  workflow_dispatch:      # кнопка Run workflow: проверяет ВСЮ историю

jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@    # ЗАПОЛНИТЬ: версия
        with:
          # ЗАПОЛНИТЬ: глубина клона
      - uses:                      # ЗАПОЛНИТЬ: экшен gitleaks и его тег
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

Отступы в YAML — только пробелы, табы он не понимает. Вложенность задаётся
ими же: `steps:` принадлежит джобу `scan`, а `with:` и `env:` — своему шагу.

Строку с токеном оставляем готовой, потому что она обманчива. `GITHUB_TOKEN`
**не надо заводить** в Settings: GitHub выдаёт его сам, отдельно на каждый
запуск, и после прогона он перестаёт действовать. Это единственный секрет
в лабе, который вы не создаёте руками — `TELEGRAM_BOT_TOKEN` и
`TELEGRAM_CHAT_ID` из задания 2 вы заводили сами.

Оба шага кладите в один джоб. У соседнего джоба свой рабочий каталог: клонируете
историю в одном, а сканируете пустоту в другом.

Про `fetch-depth`. По умолчанию `checkout` берёт **один** последний коммит.
Экшену этого мало: на событии `push` он сканирует диапазон
`<первый коммит пуша>^..<последний>` — обратите внимание на `^`, это **родитель**
первого. Если в клоне один коммит, родителя в нём нет и диапазон не собирается.
`fetch-depth: 0` означает «глубину не ограничивать», и только тогда экшену
есть от чего отсчитывать.

И сразу честно: на `push` и `pull_request` экшен смотрит **только присланные
коммиты**, а не всю историю. Токен, закоммиченный месяц назад, такой прогон
не найдёт — он зелёный. Всю историю экшен проверяет на двух других событиях,
`workflow_dispatch` и `schedule`: там диапазон не задаётся, и сканируется всё.
Поэтому `workflow_dispatch` в файле ниже не лишний — это кнопка «проверить
целиком», и нажать её стоит хотя бы один раз на каждом репозитории, который
вы получили по наследству.

Про `env:`. У `gitleaks-action` нет ни одного параметра `with:`: всё, что ему
нужно, он читает из переменных окружения. `GITHUB_TOKEN` — обязательная.

Тег пишите руками: `@v3`. Ветку `@main` брать нельзя — экшен обновят, и ваш
workflow сломается в середине сессии не по вашей вине.

И отдельно. Когда будете коммитить этот файл, ваш собственный `pre-commit`
может на него наброситься: в нём стоит строка `GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}`.
Если хук ищет просто слово `TOKEN`, он остановит коммит — и будет неправ: здесь
не секрет, а ссылка на секрет. Чините хук, а не обходите его флагом: секрет —
это `TOKEN=` с настоящим значением, а не любое упоминание слова.

Запушьте. Во вкладке Actions появится первый запуск, и он почти наверняка
зелёный: экшен смотрит коммиты этого пуша, а секретов в них нет. Красным мы
сделаем его в следующем задании — специально.

## 4. Поймать секрет по-настоящему

Проверка зелёная — значит, она ничего не нашла. Проверим, что она вообще умеет
находить.

Строку с поддельным токеном **не копируйте глазами** из этого файла: по дороге
через буфер обмена, PDF или мессенджер символы портятся, и тогда проверка
останется зелёной — сканеру просто нечего будет искать. Соберите её командой:

```bash
git switch -c leak-test
B=0OkE2rXqVn4mT7sLdB9uYcAz1WpQfH3jKgRv
printf 'SLACK_TOKEN="ghp_%s"\n' "$B" > leak.txt
grep -c 'ghp_[0-9a-zA-Z]\{36\}' leak.txt
```

Последняя команда обязана напечатать `1`. Если `0` — строка испорчена, дальше
идти бессмысленно. Токен поддельный, свой настоящий сюда не подставляйте.

```bash
git add leak.txt
git commit -m "leak test" --no-verify
git push -u origin leak-test
```

`--no-verify` здесь не жульничество, а часть задания: ваш `pre-commit` эту строку
не пропустит — значит он работает. Запомните этот момент.

Проверка станет красной уже на этом пуше, ещё до всякого Pull Request. Найдите
в логе шага gitleaks строку с файлом, номером строки и правилом — правило будет
называться `github-pat`.

Теперь откройте Pull Request из этой ветки. Проверка красная и здесь, но смотрит
она на другой диапазон: не на коммиты последнего пуша, а на все коммиты, которые
несёт этот PR. Отсюда и разница, ради которой стоит задание: пуш видит только то,
что вы прислали сейчас, PR — всё, что ветка тащит с собой.

PR не мержите: закройте его, ветку удалите. Строка с токеном останется в истории
закрытой ветки — отдельный повод подумать.

## 5. Проверка

Задания 2–4 вы делали в своём репозитории, поэтому проверка должна знать, где
он лежит **у вас на диске**. Не адрес на GitHub, а путь к клону.

Если вы создавали workflow через браузер, на github.com, — на диске его ещё нет.
Сделайте `git pull` в своём репозитории, иначе проверка честно скажет, что файла
не существует.

Из учебного каталога, где лежат хуки:

```bash
./check.py
```

Пять PASS — это задание 1. Два оставшихся workflow лежат в вашем репозитории,
поэтому путь к его клону надо назвать:

```bash
./check.py --repo ~/путь/к/своему/репозиторию
```

Ожидаемый результат:

```text
PASS: оба хука лежат в .githooks, закоммичены, исполняемы и включены
PASS: pre-commit останавливает секреты и не мешает обычным коммитам
PASS: commit-msg требует номер задачи в начале сообщения
PASS: хук обходится через --no-verify, и это нормально: он вежливость, а не защита
PASS: рабочее дерево чистое
PASS: telegram.yml: триггер push, токен и chat_id из секретов
PASS: workflow gitleaks: push и pull_request, checkout с fetch-depth: 0, экшен v3
```

Скрипт читает файлы — он не знает, запустились ли они на GitHub. Это проверяется
глазами: вкладка Actions и `SUBMISSION.md`.

## Приём

Покажите преподавателю семь PASS (`./check.py --repo ...`), вкладку Actions
своего репозитория с зелёным и красным прогоном и заполненный `SUBMISSION.md`.
Вопросы, на которые надо ответить вслух:

- почему `pre-commit` не защищает команду от утечки секрета, хотя он работает;
- что произойдёт с вашим хуком у коллеги, который склонировал репозиторий;
- почему для уведомления не понадобился свой сервер: кто кому звонит;
- чем `push` отличается от `pull_request` как события и почему с исходным
  файлом отправка ветки ничего не запускала;
- что покажет проверка gitleaks, если удалить файл с ключом отдельным
  коммитом и запушить удаление.

## Необязательно: обратный мердж в GitFlow

На зачёт не влияет. Делайте, если осталось время или дома — тема лекции,
а руками её не потрогать иначе.

На лекции мы разобрали, что релизная ветка вливается **дважды**: в main
и обратно в develop. Пропустить второй мердж легко, а счёт приходит
через релиз, когда уже не помнишь, кто что делал.

```bash
make lab3-gitflow        # без make: bash lab03-hooks/gitflow.sh
```

Развернётся репозиторий в состоянии «релиз уехал в main, а в develop его
не вернули»:

```text
main       v1.1 ──────── Merge release/1.2 (тег v1.2, фикс внутри)
develop    v1.1 ── корзина ── промокоды           ← фикса НЕТ
```

Задача: закрыть долг, не трогая main и не переписывая историю. Долг видно
одной командой, она же годится в CI как сторожевая:

```bash
git log --oneline develop..main     # непусто = в main есть то, чего нет в develop
```

Конфликт по `VERSION` будет обязательно: версию правили обе стороны. Это
ожидаемо — так написано и в исходной статье про GitFlow. Разрешайте
в пользу develop.

Проверка:

```bash
./check.py --gitflow
```

Три вещи, на которых проверка вас поймает, и каждая — отдельный урок:
`rebase` вместо мерджа переписывает историю; `cherry-pick` переносит копию
и не оставляет связи между ветками; мердж самой `release/1.2` вместо тега
