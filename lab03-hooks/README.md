# Занятие 3 · Хуки и вебхуки

Git умеет запускать ваш скрипт в момент коммита. GitHub умеет постучаться на ваш
адрес в момент события. Это два разных механизма, и путать их дорого. Сегодня вы
напишете оба, а потом заберёте написанное в свой репозиторий.

Работа делится на две части. Первая проверяется скриптом, вторая сдаётся текстом.

## Подготовка

Из корня репозитория курса:

```bash
make lab3                              # если make нет: bash lab03-hooks/setup.sh
cd ../opr-lab03/shop        # путь скрипт печатает сам
```

Хуков в репозитории нет: вы напишете их сами.

## Часть 1. Учебный репозиторий

### 1. Два хука в `.githooks`

Создайте каталог `.githooks`, а в нём два исполняемых скрипта.

`pre-commit` — не даёт закоммитить секрет. Он должен:

- отклонять файл `.env`;
- отклонять строку вида `API_KEY="AKIAIOSFODNN7EXAMPLE"`, а также `TOKEN=`,
  `SECRET=` и `PASSWORD=` с непустым значением;
- пропускать обычный код и текст, где слово «токен» просто упомянуто.

Проверяйте то, что лежит в индексе, а не в рабочей папке: `git diff --cached`.

`commit-msg` — требует номер задачи. Принимает `SHOP-12 Добавить расчёт скидки`,
отклоняет `Добавить расчёт скидки` и `shop12 добавить скидку`. Git передаёт этому
хуку один аргумент: путь к файлу с сообщением.

Оба скрипта закоммитьте. Хуки не переносятся клонированием сами по себе, поэтому
их кладут в репозиторий и включают одной командой:

```bash
git config core.hooksPath .githooks
```

### 2. Уведомление в Telegram

В каталоге `deliveries/` лежат четыре записанные доставки GitHub: тело запроса
ровно теми байтами, что пришли, и заголовок `X-Hub-Signature-256` к нему.
Секрет для всех примеров указан в `deliveries/README.md`.

Подпись — это `sha256=` и следом HMAC-SHA256 от тела на секрете. Сравнивать
строки оператором `==` нельзя, только `hmac.compare_digest`: почему именно так,
вас спросят на приёме.

Задача: уведомлять в Telegram, когда в репозитории открыли pull request, —
но только если доставка настоящая.

Напишите `notify.py`. Он получает два пути: файл с телом доставки и файл с
подписью к ней.

```bash
export WEBHOOK_SECRET=opr-2026-secret
export TELEGRAM_BOT_TOKEN=111111:TEST-TOKEN      # любая строка: никуда не уйдёт
export TELEGRAM_CHAT_ID=-1001234567890
python notify.py deliveries/pr-valid.json deliveries/pr-valid.sig
```

В PowerShell переменные задаются иначе: `$env:WEBHOOK_SECRET="opr-2026-secret"`.

Отправлять запрос никуда не надо, и это не поблажка. Токена бота у вас нет, сети
на приёмке может не быть, а поведение проверять надо. Поэтому `notify.py`
печатает запрос, который ушёл бы в Telegram: первой строкой метод и адрес,
второй — тело.

```text
POST https://api.telegram.org/bot<TELEGRAM_BOT_TOKEN>/sendMessage
{"chat_id": "<TELEGRAM_CHAT_ID>", "text": "Новый pull request #7 в student/opr-shop\n..."}
```

Тело печатайте через `json.dumps` одной строкой: переводы строк внутри текста
должны превратиться в `\n` внутри JSON, а не разорвать вывод. В `text` положите
то, ради чего уведомление вообще читают: имя репозитория и номер pull request,
дальше на ваш вкус — заголовок, автор, сколько файлов изменено.

Что должно происходить:

- подпись верна и это открытие pull request (в теле есть `pull_request`,
  `action` равен `opened`) — печатается запрос, код возврата 0;
- подпись не сошлась — не печатается ничего, код возврата не 0;
- подпись верна, но событие не про pull request (в `deliveries` это push) —
  не печатается ничего, код возврата 0: промолчать, когда сказать нечего, тоже работа;
- не задан `TELEGRAM_BOT_TOKEN` или `TELEGRAM_CHAT_ID` — не печатается ничего,
  код возврата не 0. Запрос с пустым токеном хуже, чем никакого запроса.

Жалобы пишите в stderr. stdout здесь машинный канал: в нём только запрос.

Тело доставки читайте байтами — `open(path, "rb")`, а не текстом. Подпись
считали по байтам, и любое переписывание переводов строк по дороге её ломает.
На четырёх доставках из `deliveries` разницы не видно: они в одну строку.
Поэтому проверка подсунет вашему скрипту ещё одну, собранную на месте, где тело
разбито на строки, — чтение текстом на ней разваливается. В `.sig` лежит
значение заголовка и перевод строки в конце — обрежьте его. Сравнивайте подпись
через `hmac.compare_digest`, а не оператором `==`.

Токен бота и chat_id в репозиторий не кладите. Строка
`TELEGRAM_BOT_TOKEN = "123456:AA..."` в коде — ровно тот случай, ради которого
вы час назад писали `pre-commit`. Значения по умолчанию — тот же случай в профиль:
`os.environ.get("TELEGRAM_CHAT_ID", "-100123...")` кладёт в репозиторий то же
самое, только вежливо.

Ваш же `pre-commit` может заругаться на строку `token = need_env("TELEGRAM_BOT_TOKEN")`
в `notify.py`. Это не повод отключать хук и не повод переименовывать переменную:
это повод уточнить правило. Секрет — это присвоенное значение, а не имя.

В боевом скрипте вместо `print` стоял бы `urllib.request` с заголовком
`Content-Type: application/json` и тем же телом; всё остальное осталось бы как есть.

### 3. Workflow, который ищет секреты

`pre-commit` живёт на вашей машине и снимается флагом. Проверка на стороне
GitHub так не снимается: она смотрит на то, что уже пришло в репозиторий, и
ставит красный крест в Pull Request.

Создайте `.github/workflows/gitleaks.yml`. Он должен:

- запускаться на `push` и на `pull_request`;
- забирать историю целиком: `actions/checkout@v6` с `fetch-depth: 0`;
- звать `gitleaks/gitleaks-action@v3`;
- передавать экшену `GITHUB_TOKEN` через `env:`.

Оба шага кладите в один джоб. У соседнего джоба свой рабочий каталог: клонируете
историю в одном, а сканируете пустоту в другом.

Про `fetch-depth`. По умолчанию `checkout` берёт один коммит. Секрет живёт
в истории, а не в рабочем каталоге: ключ закоммитили во вторник, в среду файл
удалили — в дереве чисто, в истории ключ лежит и прекрасно достаётся. Сканеру
нужны коммиты, поэтому `fetch-depth: 0`, то есть «глубину не ограничивать».

Про `env:`. У `gitleaks-action` нет ни одного параметра `with:`: всё, что ему
нужно, он читает из переменных окружения. `GITHUB_TOKEN` — обязательная.

Тег пишите руками: `@v3`. Ветку `@main` брать нельзя — экшен обновят, и ваш
workflow сломается в середине сессии не по вашей вине.

И отдельно. Когда будете коммитить этот файл, ваш собственный `pre-commit`
может на него наброситься: в нём стоит строка `GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}`.
Если хук ищет просто слово `TOKEN`, он остановит коммит — и будет неправ: здесь
не секрет, а ссылка на секрет. Чините хук, а не обходите его флагом: секрет —
это `TOKEN=` с настоящим значением, а не любое упоминание слова.

Здесь, в учебном репозитории, workflow не запустится: Actions живут на GitHub,
а этот репозиторий никуда не уезжает. `check.py` читает сам файл — триггеры,
глубину, тег и то, что токен уходит через `env:`. Работать он будет в части 2.

### 4. Проверка

```bash
./check.py
```

Ожидаемый результат:

```text
PASS: оба хука лежат в .githooks, закоммичены, исполняемы и включены
PASS: pre-commit останавливает секреты и не мешает обычным коммитам
PASS: commit-msg требует номер задачи в начале сообщения
PASS: хук обходится через --no-verify, и это нормально: он вежливость, а не защита
PASS: сравнение подписи идёт через hmac.compare_digest
PASS: notify.py печатает вызов sendMessage на честном pull request и молчит на остальных
PASS: токен и chat_id берутся из окружения, а не из репозитория
PASS: workflow gitleaks: push и pull_request, checkout с fetch-depth: 0, экшен v3
PASS: рабочее дерево чистое
```

## Часть 2. Свой репозиторий на GitHub

Здесь вы делаете то же самое на живом репозитории и оставляете себе рабочий
инструмент. Подойдёт любой ваш репозиторий: учебный, pet-проект, конспекты.

1. Скопируйте туда `.githooks` и включите: `git config core.hooksPath .githooks`.
2. Убедитесь, что хук срабатывает: попробуйте закоммитить строку с токеном.
3. Откройте `https://webhook.site` и скопируйте свой уникальный адрес.
4. В своём репозитории: Settings → Webhooks → Add webhook. Payload URL — адрес
   с webhook.site, Content type — `application/json`, Secret — придумайте свой,
   события — Just the push event.
5. Сделайте push и найдите доставку на webhook.site.
6. Сохраните тело запроса в файл ровно как есть, без переформатирования, и
   проверьте его своим `notify.py` со своим секретом. Подпись должна сойтись.
7. Загляните в Settings → Webhooks → Recent Deliveries: там видно код ответа,
   заголовки и кнопка Redeliver. Отправьте доставку повторно.
8. Скопируйте в свой репозиторий `.github/workflows/gitleaks.yml` и запушьте.
   Во вкладке Actions появится первый запуск. Скорее всего он зелёный: экшен
   смотрит коммиты этого пуша, а в них секретов нет.
9. Создайте ветку и добавьте в любой файл строку вида
   `SLACK_TOKEN="ghp_0OkE2rXqVn4mT7sLdB9uYcAz1WpQfH3jKgRv"`. Это не настоящий
   токен, свой сюда не подставляйте. Ваш `pre-commit` её не пропустит — значит
   он работает; закоммитьте через `--no-verify` и запомните этот момент.
10. Откройте Pull Request из этой ветки. Проверка должна стать красной. Найдите
    в логе шага gitleaks строку с файлом, номером строки и правилом.
11. PR не мержите: закройте его, ветку удалите. Строка с токеном останется
    в истории закрытой ветки — отдельный повод подумать.

Что заполнить в `SUBMISSION.md`, лежит там же.

## Приём

Покажите преподавателю девять PASS и заполненный `SUBMISSION.md`. Вопросы,
на которые надо ответить вслух:

- почему `pre-commit` не защищает команду от утечки секрета, хотя он работает;
- что произойдёт с вашим хуком у коллеги, который склонировал репозиторий;
- зачем вебхуку подпись, если адрес знаете только вы.
- почему `notify.py` печатает запрос, а не отправляет его, и что в коде
  изменится в тот день, когда токен бота у вас появится;
- что покажет проверка gitleaks, если удалить файл с ключом отдельным
  коммитом и запушить удаление.
