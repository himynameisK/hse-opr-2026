# Занятие 3 · Хуки и вебхуки

Git умеет запускать ваш скрипт в момент коммита. GitHub умеет постучаться на ваш
адрес в момент события. Это два разных механизма, и путать их дорого. Сегодня вы
напишете оба, а потом заберёте написанное в свой репозиторий.

Работа делится на две части. Первая проверяется скриптом, вторая сдаётся текстом.

## Подготовка

Из корня репозитория курса:

```bash
make lab3
cd ~/opr-lab03/shop
```

Хуков в репозитории нет: вы напишете их сами.

## Часть 1. Учебный репозиторий

### 1. Два хука в `.githooks`

Создайте каталог `.githooks`, а в нём два исполняемых скрипта.

`pre-commit` — не даёт закоммитить секрет. Он должен:

- отклонять файл `.env`;
- отклонять строку вида `API_KEY="AKIAIOSFODNN7EXAMPLE"`, а также `TOKEN=`,
  `SECRET=` и `PASSWORD=` с непустым значением;
- пропускать обычный код и текст, где слово «токен» просто упомянуто.

Проверяйте то, что лежит в индексе, а не в рабочей папке: `git diff --cached`.

`commit-msg` — требует номер задачи. Принимает `SHOP-12 Добавить расчёт скидки`,
отклоняет `Добавить расчёт скидки` и `shop12 добавить скидку`. Git передаёт этому
хуку один аргумент: путь к файлу с сообщением.

Оба скрипта закоммитьте. Хуки не переносятся клонированием сами по себе, поэтому
их кладут в репозиторий и включают одной командой:

```bash
git config core.hooksPath .githooks
```

### 2. Проверка подписи вебхука

В каталоге `deliveries/` лежат четыре записанные доставки GitHub: тело запроса
ровно теми байтами, что пришли, и заголовок `X-Hub-Signature-256` к нему.
Секрет для всех примеров указан в `deliveries/README.md`.

Напишите `verify.py`, который отвечает на один вопрос: подпись настоящая или нет.

- тело читается из stdin;
- секрет берётся из переменной окружения `WEBHOOK_SECRET`;
- подпись берётся из переменной окружения `X_HUB_SIGNATURE_256`;
- код возврата 0, если подпись верна, и любой другой, если нет.

Подпись это `sha256=` и следом HMAC-SHA256 от тела на секрете. Сравнивать строки
оператором `==` нельзя: используйте `hmac.compare_digest`. Почему именно так —
вопрос, который вам зададут при приёме.

### 3. Проверка

```bash
./check.py
```

Ожидаемый результат:

```text
PASS: оба хука лежат в .githooks, закоммичены, исполняемы и включены
PASS: pre-commit останавливает секреты и не мешает обычным коммитам
PASS: commit-msg требует номер задачи в начале сообщения
PASS: хук обходится через --no-verify, и это нормально: он вежливость, а не защита
PASS: verify.py принимает обе честные доставки и отвергает подменённую и чужую
PASS: сравнение подписи идёт через hmac.compare_digest
PASS: рабочее дерево чистое
```

## Часть 2. Свой репозиторий на GitHub

Здесь вы делаете то же самое на живом репозитории и оставляете себе рабочий
инструмент. Подойдёт любой ваш репозиторий: учебный, pet-проект, конспекты.

1. Скопируйте туда `.githooks` и включите: `git config core.hooksPath .githooks`.
2. Убедитесь, что хук срабатывает: попробуйте закоммитить строку с токеном.
3. Откройте `https://webhook.site` и скопируйте свой уникальный адрес.
4. В своём репозитории: Settings → Webhooks → Add webhook. Payload URL — адрес
   с webhook.site, Content type — `application/json`, Secret — придумайте свой,
   события — Just the push event.
5. Сделайте push и найдите доставку на webhook.site.
6. Сохраните тело запроса в файл ровно как есть, без переформатирования, и
   проверьте его своим `verify.py` со своим секретом. Подпись должна сойтись.
7. Загляните в Settings → Webhooks → Recent Deliveries: там видно код ответа,
   заголовки и кнопка Redeliver. Отправьте доставку повторно.

Что заполнить в `SUBMISSION.md`, лежит там же.

## Приём

Покажите преподавателю семь PASS и заполненный `SUBMISSION.md`. Вопросы,
на которые надо ответить вслух:

- почему `pre-commit` не защищает команду от утечки секрета, хотя он работает;
- что произойдёт с вашим хуком у коллеги, который склонировал репозиторий;
- зачем вебхуку подпись, если адрес знаете только вы.
