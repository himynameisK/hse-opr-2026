# Занятие 5 · Процессы, сигналы, systemd

Четыре заявки дежурной смены, минут сорок.

## Где это делается

**Ваша виртуальная машина с Linux — основной вариант.** Нужны права root
через `sudo`.

```bash
sudo bash lab05-linux/setup.sh
```

Если чего-то не хватает, `setup.sh` скажет прямо чего:

```bash
sudo apt-get update && sudo apt-get install -y python3 procps tmux passwd iproute2
```

### Если виртуалки не оказалось

Первые три заявки делаются в WSL 2 и в обычном контейнере, без особых флагов.
Четвёртая — только там, где systemd загрузил систему: в контейнере его нет,
и проверка эту заявку пропустит.

```bash
wsl --install                                        # Windows
docker run -it --rm -v "$PWD":/course debian:12 bash  # где есть Docker
```

В WSL 2 systemd включается двумя строками, и тогда делаются все четыре:

```bash
printf '[boot]\nsystemd=true\n' | sudo tee /etc/wsl.conf   # потом wsl --shutdown
```

На macOS и в Windows **напрямую** задание не живёт: там нет ни `/proc`,
ни сигналов в том виде, о котором идёт речь.

## Зачем это нужно

**Команда показывает не то, что происходит в системе.** Место занято файлом,
которого нет. Число есть, а файла с ним нет. Процессов нет, а места в таблице
заняты. Сервис работает, а в системе его нет. Все четыре заявки — про этот
разрыв, и `chmod 777` с перезагрузкой не лечат ни одну.

## Заявки

Заявки 2, 3 и 4 независимы: застряли — беритесь за следующую.
**Заявка 1 — исключение: там нельзя убивать процесс**, иначе данные потеряны
без возврата. Прочитайте её целиком, прежде чем нажимать.

### Заявка 1. «Файл удалили, место не вернулось»

> Кончалось место, дежурный удалил самый толстый лог — `/var/log/opr-audit.log`,
> 33 МБ. Файла нет, свободного места не прибавилось. А журнал нужен в отчёт.
> Служба, которая его писала, всё ещё работает.

Последней строкой `setup.sh` печатает колонку `Used` из `df /var/log` до `rm`
и сразу после: числа совпали. Проверьте сами и найдите, кто держит удалённый
файл открытым.

Восстановите содержимое в `/var/tmp/opr-lab05/restored.log`.

**Службу не убивать.** Её дескриптор — единственная дорога к данным, эталона
нигде нет, второй попытки с тем же содержимым не будет. Символическая ссылка
не считается: это указатель на чужой дескриптор, он закроется вместе
с процессом. Жёсткая тоже не выйдет — `/proc` отдельная файловая система.

Когда получите PASS — и только тогда — можно `kill`, а потом снова `df`:
разница в колонке `Used` и есть те самые 33 МБ. После этого проверка по заявке
даст FAIL, так и задумано.

### Заявка 2. «Вывод был на экране, а файла нет»

> Ночной пересчёт тарифов напечатал в консоль контрольную сумму выгрузки.
> Сохранить её забыли, а в отчёт она нужна. Сеанс, где это считалось, висит
> отсоединённым с прошлой недели.

```bash
tmux ls          # четыре сессии, нужная одна
```

Найдите сумму и запишите её в `/var/tmp/opr-lab05/checksum.txt`.

`grep` по диску бесполезен: истории панели нет ни в одном файле, она живёт
в памяти процесса `tmux: server`. Пока он жив, история читается целиком —
вместе с тем, что уехало за край экрана.

Выйдете из панели через `exit` — сессия и история умрут, а сумма случайная:
у проверки от неё только sha256. Отсоединяться надо `Ctrl-b d`.

### Заявка 3. «Ничего не запускается: fork: Resource temporarily unavailable»

> У пользователя `opr` перестала запускаться выгрузка отчётов. Памяти свободно,
> места на диске полно.

```bash
su -s /bin/bash opr -c /opt/opr-lab05/t3/report.sh      # так падает
ps -u opr -o pid,ppid,stat,args
```

Найдите, что заняло таблицу процессов, и верните выгрузку в работу. `kill -9`
по тому, что вы там увидите, ничего не даст — сначала поймите почему, из ответа
прямо следует, что делать. Перезагрузка машины ответом не считается.

Текст службы лежит в `/usr/local/sbin/opr-collector` и читается целиком:
поломка там в одной отсутствующей строке.

Зачем это знать: в контейнере ваше приложение — PID 1, и забирать коды возврата
его детей больше некому. Отсюда растут `docker run --init` и `tini`.

### Заявка 4. «Сервис жил в tmux, машину перезагрузили»

> API держат запущенным в tmux на сервере — так его поднял человек, который уже
> не работает. После плановой перезагрузки API не поднялся, и чем он запускался,
> никто не знает.

Нужна виртуальная машина или WSL с systemd.

```bash
ss -ltnp | grep 8080            # кто держит порт
pstree -ps <pid>                # и чей это потомок
```

Сделайте так, чтобы API поднималось само — после перезагрузки и после падения.
Юнит напишите свой, назвать можете как угодно: проверка спрашивает не имя,
а cgroup процесса, который отвечает на порту. Чем его запускали руками, осталось
в истории панели.

Копию в tmux погасите: два процесса на один порт не встанут, и ваш юнит
не запустится — `Address already in use` в `journalctl`.

## Чем смотреть

```text
ps -eo pid,ppid,stat,etime,cmd    кто есть, в каком состоянии, как давно
ps -u opr -o pid,ppid,stat,args   то же по одному пользователю
pstree -ps <pid>                  вся цепочка родителей до PID 1
ls -l /proc/<pid>/fd              открытые дескрипторы процесса
stat -L /proc/<pid>/fd/<номер>    inode за дескриптором: размер и Links
find /proc/[0-9]*/fd -lname '* (deleted)'    кто держит удалённые файлы
kill -l                           номера сигналов
tmux ls                           какие сессии есть и кто к ним подключён
tmux attach -t имя                зайти; выйти без закрытия — Ctrl-b d
tmux capture-pane -p -S - -t имя  вся история панели, включая уехавшее за край
ss -ltnp                          кто слушает порт
systemctl status / is-active / is-enabled    работает ли, поднимется ли
journalctl -u юнит -b             логи юнита с этой загрузки
df путь                           занятое место: до и после
```

## Вопросы на подумать

Почему `rm` не освободил место и в какой момент оно всё-таки освободилось?
Почему `logrotate` не удаляет файл, а переименовывает его и просит службу
переоткрыть лог?

Зомби — это ошибка завершившегося процесса или его родителя? Кто забрал записи
его детей, когда родитель умер?

`SIGKILL` перехватить нельзя. Почему тогда `kill -9` иногда не убивает процесс
и в каком он при этом состоянии?

tmux пережил бы обрыв связи, но не пережил перезагрузку. В чём тогда разделение
труда между tmux и systemd? И почему `start` и `enable` — две разные команды?

## Если всё сломалось

```bash
sudo bash lab05-linux/reset.sh
```

Закрывает учебные сессии tmux, останавливает службы, убирает юнит из заявки 4
и разворачивает всё с нуля. Запускать можно сколько угодно раз: после убитой
раньше времени службы, после `exit` не в той панели, после перезагрузки
виртуалки. Починенное откатится, а содержимое журнала и контрольная сумма
сгенерируются заново — поэтому вывод проверки сохраняйте по ходу дела.

## Проверка

сессии tmux, `su` за `opr` и `systemctl`.
