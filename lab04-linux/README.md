# Занятие 4 · Файлы, права, процессы

Два задания, вместе около сорока минут. Каждое сдаётся отдельно.

## Где это делается

**Ваша виртуальная машина с Linux — основной и ожидаемый вариант.** Её вы ставили
к этому занятию, и в ней всё работает без дополнительных настроек: нужны только
права root через `sudo`.

Окружение живёт **весь блок**: занятия 5 и 6 (процессы, systemd, память) в контейнере
уже не покажешь, там нужна настоящая система. Не удаляйте виртуалку после пары.

```bash
# внутри вашей виртуалки
sudo bash lab04-linux/setup.sh
```

На обычной Ubuntu или Debian ничего доустанавливать не придётся. Если система
минимальная и чего-то не хватает, `setup.sh` скажет прямо чего:

```bash
sudo apt-get update && sudo apt-get install -y python3 passwd util-linux e2fsprogs
```

### Если виртуалки не оказалось

Запасные варианты. Работают, но занятия 5 и 6 на них пройти не выйдет —
виртуалку всё равно придётся поставить.

```bash
# Windows: WSL2 — там настоящее ядро Linux, всё работает как в виртуалке
wsl --install

# macOS: виртуалка одной командой
brew install multipass && multipass launch --name opr && multipass shell opr

# любая система, где уже есть Docker
docker run -it --rm --privileged -v "$PWD":/course debian:12 bash
```

⚠️ Для Docker флаг **`--privileged` обязателен**: без него не смонтировать учебный
раздел, и четвёртая заявка не развернётся. В виртуальной машине и в WSL2 флаг
не нужен — там монтирование доступно само.

На macOS и в Windows **напрямую** задание не живёт вообще: там другая модель прав,
нет `/proc` и нет точек монтирования, о которых идёт речь. И контейнер, и WSL2 —
это Linux, запущенный поверх вашей системы, а не ваша система.

## Зачем это нужно

Четыре заявки из дежурной смены. Все четыре — то, с чем вы столкнётесь на первой же
работе, и все четыре выглядят как мистика, пока не знаешь, куда смотреть.

Общее у них одно: **сообщение об ошибке называет симптом, а не причину.**
«Permission denied» приходит от трёх разных вещей, «No space left on device» —
от двух. Чинить, не поставив диагноз, здесь не выйдет: `chmod 777` не лечит
ни одну из них.

## Задание 1. Четыре заявки

Каждая независима: застряли на одной — беритесь за следующую. Работы минут тридцать.

Починенный скрипт печатает своё слово:

```bash
./t1/script.sh      # должно напечатать ok-1
```

### Заявка 1. «Деплой-скрипт не запускается»

> Выкатывали релиз, скрипт лежит на месте, запускаться отказывается.

Разберитесь и почините причину. `chmod 777` — не ответ: это ещё и право записи
для всех, а просили не это.

### Заявка 2. «На другой машине — bad interpreter, хотя bash стоит»

> Тот же скрипт, соседний сервер. Ругается, что нет интерпретатора.
> `which bash` показывает `/bin/bash`. Мистика.

Сообщение бывает двух видов — `bad interpreter` или `cannot execute: required file
not found`, зависит от версии bash. Смысл один: **ядро не нашло то, что написано
в первой строке файла.** Ищите глазами то, чего в выводе `cat` не видно.

Чинить надо файл, а не привычку писать `bash script.sh` перед всем подряд:
в systemd или в CI такой скрипт запускают как исполняемый, и он снова упадёт.

### Заявка 3. «Навели порядок в правах — перестало читаться всё»

> Коллега решил починить права и прошёлся `chmod -R 644` по каталогу приложения.
> Теперь ничего не открывается. На самих файлах права при этом правильные.

Права на файле действительно в порядке — посмотрите сами. Причина этажом выше,
и она не одна. Есть команда, которая показывает права на **каждом шаге пути**
и пальцем тычет в то место, где всё оборвалось.

Чинится это тоже не в лоб: `chmod -R 755` сделает исполняемыми и конфиги,
а это мусор. Загляните в `man chmod` и найдите, чем `X` отличается от `x`.

### Заявка 4. «Места полно, а файл не создаётся»

> На разделе `/srv/cache` приложение не может создать файл: «No space left on device».
> `df` показывает, что занято 1%. Дежурный трижды перепроверил — место есть.

У файловой системы два независимых запаса, и кончиться может любой. `df` показывает
только один из них.

На разделе лежат данные, которые **терять нельзя**: два отчёта и конфиг в `/srv/cache/data`.
Почистить надо то, что съело ресурс, а не всё подряд — проверка это увидит.

Вопрос на подумать: почему нельзя просто «добавить inode», как добавляют место?

### Чем смотреть

```text
ls -l   /  ls -ld       биты файла и биты самого каталога — разные команды
namei -l путь           права на каждом шаге пути, от / до файла
head -1 файл            первая строка: шебанг
cat -A  файл            невидимое: ^M это \r, $ это конец строки
file    файл            «with CRLF line terminators» — прямым текстом
df / df -i путь         два запаса файловой системы: байты и inode
du -s --inodes каталог  сколько inode съел каталог (GNU coreutils 8.31+)
find каталог -type f | wc -l    то же самое, если du такого не умеет
id                      кто вы сейчас
```

Не запускайте скрипты через `sh`: dash на те же случаи отвечает просто «not found»,
и вы потеряете полчаса.

## Задание 2. Общий каталог для команды
Два человека работают над одним проектом и складывают файлы в общий каталог.
Требования до скуки обычные: оба кладут туда файлы, оба видят файлы друг друга,
и никто не стирает чужое — ни со зла, ни случайным `rm *` в неудачный момент.

Правами `rwx` это не решается. Право на запись в каталог — это право менять
список имён в нём, то есть создавать и удалять любые записи, а не только свои.
Разрешив коллеге создавать файлы, вы тем же движением разрешили ему стирать ваши.

### Задание

Настройте `/srv/shop/shared` так, чтобы:

1. `alice` и `bob` могли создавать в нём файлы;
2. каждый мог прочитать файл, созданный другим;
3. ни один не мог удалить чужой файл, а свой — мог;
4. новый файл в каталоге доставался группе `shop`, а не личной группе создателя;
5. `carol` не попадала в каталог вовсе.

Пользователей и группы трогать не надо: они уже заведены, `alice` и `bob` уже
в `shop`, `carol` — нарочно нет. Всё делается на самом каталоге, и это две
команды. Ни одного файла писать не нужно — занятие про права, а не про скрипты.

Пункт 4 стоит отдельно не случайно. Без него в каталоге заводятся файлы с
группой `alice` и группой `bob`, которые друг другу никто, и «общий каталог»
живёт ровно до первого `ls -l`.

Владельца каталога не меняйте, он должен остаться за `root`. Почему — увидите
сами, если попробуете отдать каталог `alice` и потом запустить проверку.

Смотреть на результат: `ls -ld /srv/shop/shared` и `ls -l /srv/shop/shared`.
Перевоплотиться в пользователя: `su - alice`, обратно — `exit`.

### Грабли, про которые надо знать заранее

**Наследование группы и `umask` — разные механизмы, и они спорят.** Бит SGID на
каталоге решает, какая *группа* достанется новому файлу. Какие *права* достанутся
этой группе, он не решает — это решает `umask` процесса, который файл создал. При
`umask 022` новый файл выходит `rw-r--r--`: группа его прочитает и не изменит.
Чтобы `bob` мог дописать в файл `alice`, нужен `umask 002` — а он живёт в профиле
оболочки, а не на каталоге.

Поэтому **мы этого не требуем**. В задании стоит «читать чужие», а не «дописывать
в чужие», и проверка сама выставляет `umask 022` перед каждым действием, чтобы
результат не зависел от настроек вашей оболочки. Но знать надо: в настоящем общем
каталоге одного SGID мало, рядом всегда стоит `umask 002` в профиле или ACL
по умолчанию.

**Почему `echo текст >> чужой-файл` может не пройти даже с `umask 002`.** Если
попробуете и получите `Permission denied` на файле с честными `rw-rw-r--`, вы не
сошли с ума. В sticky-каталоге ядро отдельно запрещает открывать чужой файл
с флагом `O_CREAT`, а `>>` в оболочке всегда его добавляет; без `O_CREAT` та же
запись проходит. Это `fs.protected_regular` — защита от подмены файлов в общих
каталогах; и Debian, и Ubuntu ставят ему значение `2`, то есть распространяют
и на каталоги, открытые только группе. Разбирать её на занятии не надо,
достаточно узнать в лицо.

**`sed -i` по чужому файлу в таком каталоге тоже не пройдёт.** Он не правит файл
на месте, а пишет временный и переименовывает его поверх исходного — а
переименование в sticky-каталоге это ровно то, что там запрещено:

```text
sed: cannot rename /srv/shop/shared/sedwFBcEx: Operation not permitted
```
