# Занятие 4 · Файлы, права, процессы

Три задания. Вместе — около часа, каждое можно сдавать отдельно.

## Где это делается

Нужен **Linux, где вы root**: виртуальная машина, WSL или контейнер — нам всё равно.
На macOS и в Windows напрямую задание не живёт: там другие права, нет `/proc`
и нет точек монтирования, о которых идёт речь.

Поставить окружение стоит **один раз на весь блок**: занятия 5 и 6 (процессы,
systemd, память) в контейнере уже не покажешь, там нужна настоящая система.

```bash
# Windows — одна команда, без виртуальной машины
wsl --install

# macOS — виртуалка одной командой
brew install multipass && multipass launch --name opr && multipass shell opr

# если уже есть Docker и хочется быстро
docker run -it --rm -v "$PWD":/course debian:12 bash
```

## Подготовка

```bash
# внутри вашего Linux, из каталога курса
sudo bash lab04-linux/setup.sh            # развернёт /opt/opr-lab04
```

В голом контейнере может не быть Python и `useradd` — `setup.sh` скажет прямо,
чего не хватает. Ставится одной строкой:

```bash
apt-get update && apt-get install -y python3 passwd util-linux
```

## Задание 1. Пять сломанных скриптов
Файл на месте, `ls -l` показывает `rwxr-xr-x`, а система отвечает «Permission
denied». Это не мистика: между вашим `./script.sh` и запущенным процессом стоит
`execve`, и у него несколько разных поводов сказать «нет». Сегодня вы увидите
пять и почините каждый.

Работы здесь минут на двадцать. Пять скриптов, пять слов — больше ничего.

### Что надо сделать

Каждый `script.sh`, когда его починят, печатает своё слово: `ok-1` … `ok-5`.

```bash
./s1/script.sh      # должно напечатать ok-1
```

Что где сломано — выясняете вы. Поломок пять, каждая встречается ровно один раз:

- у файла нет бита `x`;
- файл приехал с Windows: в конце каждой строки лишний байт `\r`, в том числе
  в строке с шебангом;
- в шебанге указан интерпретатор, которого в этой системе нет;
- у каталога на пути к файлу нет бита `x`;
- файл лежит на файловой системе, смонтированной с `noexec`.

Чинить надо причину, а не симптом: в шебанге — рабочий путь к интерпретатору,
а не привычка писать `bash script.sh` перед всем подряд. И бит `x` ставят
командой `chmod +x`, а не `chmod 777`: 777 — это ещё и право записи для всех,
кто есть в системе, а просили не это.

### Про `noexec` — прочитайте до того, как начнёте

Один скрипт (это `s3`) лежит на разделе, смонтированном с опцией `noexec`. Там
не запускается ничего и ни у кого — ни у вас, ни у root: это свойство
монтирования, а не файла. Биты прав при этом честные, `rwxr-xr-x`.

Перемонтировать раздел вы, скорее всего, не сможете: в контейнере это вообще не
ваш mount. И не надо. В жизни `/tmp`, `/home` и флешки монтируют с `noexec`
намеренно, и ваша задача — не снять защиту, а сделать работу. Запрет стоит на
`execve`, читать файл никто не запрещал. Значит, лечения два:

- запустить файл интерпретатором: `bash script.sh`;
- скопировать файл на обычную файловую систему и запустить копию.

Поэтому `s3` и сдаётся иначе. Положите в `s3/` исполняемый `run.sh`, который
печатает то же слово, что и `script.sh`. Проверка делает `cd s3 && ./run.sh`.

Две тонкости. Первая: перед запуском проверка подменяет слово внутри
`script.sh` на свежее — поэтому `echo ok-3` в `run.sh` не пройдёт, и заранее
сделанная копия тоже: копировать и запускать надо внутри `run.sh`, в момент
запуска. Вторая: сам `s3/script.sh` — символическая ссылка на раздел с `noexec`,
и она должна такой остаться. Если подменить её обычным файлом, задача исчезнет
вместе с разделом; проверка это видит и скажет.

### Чем смотреть

```text
ls -l  /  ls -ld      биты файла и биты самого каталога — это разные команды
namei -l путь         права на каждом шаге пути, от / до файла
head -1 файл          первая строка: шебанг
cat -A файл           невидимое: ^M — это \r, $ — конец строки
findmnt -T файл       на каком разделе файл и с какими опциями он смонтирован
id                    кто вы сейчас
```

Читайте текст ошибки целиком. «bad interpreter» и «cannot execute: required
file not found» — это не про ваш файл, а про интерпретатор из шебанга: его
не нашли. Формулировка зависит от версии bash, смысл один. Заметьте: два разных
скрипта из пяти отвечают этой фразой одинаково — по ней их не различить, различит
`cat -A` и `head -1`. Ровно так же неразличимы на слух и две «Permission denied»:
`ls -l` и `ls -ld` — разные команды не просто так. И не запускайте скрипты через
`sh`: dash на тот же случай отвечает просто «not found», и вы потеряете полчаса.

## Задание 2. Журнал, которого нет, а место занято

На сервере кончилось место. Дежурный нашёл самый толстый файл — `/var/log/opr-audit.log` —
и удалил его. Место не вернулось, а журнал за сегодня нужен в отчёт. Служба, которая
его писала, всё ещё работает.

Это одна из самых частых аварий дежурной смены, и чинится она одной командой — если
знать, где лежит файл, у которого больше нет имени.

### 1. Посмотрите, что место занято

Последней строкой `setup.sh` печатает колонку `Used` из `df /var/log` — снятую до `rm`
и сразу после него:

```text
df /var/log, колонка Used: до rm 43593212, после rm 43593212 (1K-блоков).
```

Числа совпали. Разойтись они могут на считанные килобайты — это соседние записи на
диск, а не наши 33 МБ. Убедитесь сами:

```bash
ls -l /var/log/opr-audit.log     # No such file or directory
df /var/log                      # Used — всё то же число
```

Файла нет, а его 33 МБ никуда не делись. Имя и содержимое — разные вещи: `rm` снимает
ссылку из каталога, а данные живут, пока на inode кто-то ссылается. Ссылку из каталога
сняли — осталась ссылка из таблицы открытых файлов работающего процесса.

### 2. Найдите держателя

Открытые файлы видны в `/proc`, и только root видит чужие. Годится любой способ:

```bash
find /proc/[0-9]*/fd -lname '* (deleted)' -printf '%p -> %l\n' 2>/dev/null
ls -l /proc/[0-9]*/fd/* 2>/dev/null | grep deleted
ps aux | grep opr-auditd      # если ps установлен: в базовых образах его нет
lsof +L1                      # если установлен lsof
```

На живой машине строк будет несколько: удалённые файлы держат открытыми и другие
службы, это нормально. Ваша — та, где справа `/var/log/opr-audit.log (deleted)`.

Находку рассмотрите:

```bash
ls -l /proc/<pid>/fd
stat -L /proc/<pid>/fd/<номер>
```

В `ls` — стрелка на `/var/log/opr-audit.log (deleted)`. В `stat` — `Links: 0` и честный
размер: inode, на который не ссылается ни один каталог и который всё ещё существует.

### 3. Восстановите

Верните содержимое в файл `/var/tmp/opr-lab04/restored.log`.

Службу не убивать. Её дескриптор — единственная дорога к данным, эталон нигде не лежит
(у проверки только sha256), и второй попытки с тем же содержимым не будет.

Через `/proc` файл читается как обычный: хватит одной команды копирования. Символическая
ссылка на `/proc/<pid>/fd/<номер>` не считается: это не копия, а указатель на чужой
дескриптор, который закроется вместе с процессом. Жёсткая ссылка тоже не выход — `ln`
без `-s` ответит `Invalid cross-device link`: `/proc` отдельная файловая система, да и
новое имя inode с `Links: 0` уже не получит.

Каталог `/var/tmp`, а не `/tmp`, выбран не случайно: `/tmp` система вправе вычистить
при перезагрузке, `/var/tmp` — нет.

Обратите внимание на режим в `ls -l`: дескриптор открыт на запись (`l-wx`), а читаете
вы его всё равно. `/proc/<pid>/fd/<номер>` — не сам дескриптор, а дорога к inode:
открывается он заново и на ваших условиях.

### 4. Проверка

```bash
sudo python3 check.py
```

Ожидаемый результат:

```text
PASS: состояние занятия на месте: setup.sh отработал
PASS: служба жива (pid 1234), удалённый журнал всё ещё открыт на дескрипторе 9
PASS: /var/tmp/opr-lab04/restored.log на месте, обычный файл, размер совпал (33996012 байт)
PASS: содержимое совпало с эталоном побайтово: sha256 тот же
```

Сохраните этот вывод в `SUBMISSION.md` сейчас: после шага 5 повторить его будет нечем.

### 5. Теперь можно и убить

Когда четыре PASS получены — и только теперь:

```bash
df /var/log
kill <pid>
sleep 1
df /var/log
```

Разница в колонке Used — те самые 33 МБ. Вот теперь `rm` сработал до конца.

`sleep` здесь не для красоты: процесс умирает не мгновенно, и `df` сразу после `kill`
покажет старое число — блоки к этому моменту ещё не освобождены.

С этого момента `check.py` четырёх PASS уже не даст: второй строкой будет FAIL, службы
больше нет. Так и задумано — задание принимается по выводу из шага 4.

Если убили процесс раньше времени, содержимое потеряно навсегда, и это не фигура речи.
Запустите `setup.sh` заново: он поднимет новую службу и новый журнал с другим содержимым.
Там же ищите спасение, если виртуалку или контейнер успели перезагрузить.

## Задание 3. Общий каталог для команды
Два человека работают над одним проектом и складывают файлы в общий каталог.
Требования до скуки обычные: оба кладут туда файлы, оба видят файлы друг друга,
и никто не стирает чужое — ни со зла, ни случайным `rm *` в неудачный момент.

Правами `rwx` это не решается. Право на запись в каталог — это право менять
список имён в нём, то есть создавать и удалять любые записи, а не только свои.
Разрешив коллеге создавать файлы, вы тем же движением разрешили ему стирать ваши.

### Задание

Настройте `/srv/shop/shared` так, чтобы:

1. `alice` и `bob` могли создавать в нём файлы;
2. каждый мог прочитать файл, созданный другим;
3. ни один не мог удалить чужой файл, а свой — мог;
4. новый файл в каталоге доставался группе `shop`, а не личной группе создателя;
5. `carol` не попадала в каталог вовсе.

Пользователей и группы трогать не надо: они уже заведены, `alice` и `bob` уже
в `shop`, `carol` — нарочно нет. Всё делается на самом каталоге, и это две
команды. Ни одного файла писать не нужно — занятие про права, а не про скрипты.

Пункт 4 стоит отдельно не случайно. Без него в каталоге заводятся файлы с
группой `alice` и группой `bob`, которые друг другу никто, и «общий каталог»
живёт ровно до первого `ls -l`.

Владельца каталога не меняйте, он должен остаться за `root`. Почему — увидите
сами, если попробуете отдать каталог `alice` и потом запустить проверку.

Смотреть на результат: `ls -ld /srv/shop/shared` и `ls -l /srv/shop/shared`.
Перевоплотиться в пользователя: `su - alice`, обратно — `exit`.

### Грабли, про которые надо знать заранее

**Наследование группы и `umask` — разные механизмы, и они спорят.** Бит SGID на
каталоге решает, какая *группа* достанется новому файлу. Какие *права* достанутся
этой группе, он не решает — это решает `umask` процесса, который файл создал. При
`umask 022` новый файл выходит `rw-r--r--`: группа его прочитает и не изменит.
Чтобы `bob` мог дописать в файл `alice`, нужен `umask 002` — а он живёт в профиле
оболочки, а не на каталоге.

Поэтому **мы этого не требуем**. В задании стоит «читать чужие», а не «дописывать
в чужие», и проверка сама выставляет `umask 022` перед каждым действием, чтобы
результат не зависел от настроек вашей оболочки. Но знать надо: в настоящем общем
каталоге одного SGID мало, рядом всегда стоит `umask 002` в профиле или ACL
по умолчанию.

**Почему `echo текст >> чужой-файл` может не пройти даже с `umask 002`.** Если
попробуете и получите `Permission denied` на файле с честными `rw-rw-r--`, вы не
сошли с ума. В sticky-каталоге ядро отдельно запрещает открывать чужой файл
с флагом `O_CREAT`, а `>>` в оболочке всегда его добавляет; без `O_CREAT` та же
запись проходит. Это `fs.protected_regular` — защита от подмены файлов в общих
каталогах; и Debian, и Ubuntu ставят ему значение `2`, то есть распространяют
и на каталоги, открытые только группе. Разбирать её на занятии не надо,
достаточно узнать в лицо.

**`sed -i` по чужому файлу в таком каталоге тоже не пройдёт.** Он не правит файл
на месте, а пишет временный и переименовывает его поверх исходного — а
переименование в sticky-каталоге это ровно то, что там запрещено:

```text
sed: cannot rename /srv/shop/shared/sedwFBcEx: Operation not permitted
```
